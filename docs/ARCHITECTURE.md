# 系统架构设计（ARCHITECTURE）

「多表人员信息汇总助手」（`people-info-merge`，v1.0.0）采用**单文件核心引擎 + 分阶段 CLI 契约 + 显式人工确认点 + 双后端输出**的轻量架构。全部数据处理在本地内存完成，不依赖外部网络或数据库，专为 HR、行政与项目助理的多源人员表汇总场景设计。

---

### 核心职责边界
- **`SKILL.md`**：定义上层交互协议与安全护栏，约束调用方必须遵循“先探测 → 推荐键 → 人工确认 → 再合并”的顺序，禁止跳过确认点静默合并。
- **`scripts/people_merge.py`**：承载全部解析、归一化、键推荐、表连接、冲突保留、三 Sheet 导出、报告生成、端到端自测与 AST 安全审计逻辑；默认零第三方依赖。
- **`scripts/package_skill.py`**：负责交付前校验 `SKILL.md` 位于包根层级、过滤缓存及临时产物，确保产物远小于 10MB 体积上限。
- **`references/`**：将使用规范、输出契约、格式矩阵、隐私安全与限制拆分为独立参考文档，保持主入口简洁。
- **`tests/` 与 `examples/sample_data/`**：提供脱敏样本与 24 项可离线执行的 `unittest` 回归验证。

## 2. 五子命令与核心数据流

核心引擎 `scripts/people_merge.py` 暴露 5 个子命令：3 个构成主业务流水线（`inspect`、`suggest-keys`、`merge`），2 个构成质量与安全自检闭环（`selftest`、`selfcheck`）。

### 主业务数据流

```text
[多源输入文件]
(.xlsx/.xlsm/.ods/HTML伪.xls/SpreadsheetML/.csv/.tsv/.txt/旧.xls)
       │
       ▼  1. 只读探测（内容嗅探 + 表头/样本提取）
┌──────────────────┐
│  inspect         │
└────────┬─────────┘
         │ 输出
         ▼
   profile.json  （各表格式、表头、样本行与基础画像）
         │
         ▼  2. 候选关联键打分与跨表重合度计算
┌──────────────────┐
│  suggest-keys    │
└────────┬─────────┘
         │ 输出
         ▼
    keys.json    （候选关联键评分与重合度证据）
         │
         ▼
╔══════════════════════════════════════════════════════╗
║  [确认点一（必须）] 用户确认最终使用的关联键（姓名/工号）   ║
║  [确认点二（建议）] 一键确认未匹配记录处置策略：           ║
║    separate_sheet(默认推荐) | keep_marked | drop      ║
╚════════╤═════════════════════════════════════════════╝
         │ 写入合并计划                   ▲ 可复用历史方案
         ▼                                │ (--recipe)
    plan.json  ◄──────────────────── recipe.json
         │                                ▲ (--save-recipe)
         ▼  3. 归一化 + 关联连接 + 冲突保留 + 双后端写出
┌──────────────────┐
│  merge           │  (--backend auto | stdlib | openpyxl)
└────────┬─────────┘
         │ 输出
         ├───────────────────────────┐
         ▼                           ▼
   汇总结果.xlsx                .report.json
  ├── Sheet1: 汇总结果         （机器可读统计与冲突明细）
  ├── Sheet2: 合并日志
  └── Sheet3: 未匹配记录
```

### 辅助治理子命令

```text
┌──────────────────┐     阶段1：CSV 多表合并验证
│  selftest        │ ──► 阶段2：HTML 伪 .xls + .ods + .tsv 跨格式合并验证
└──────────────────┘

┌──────────────────┐     ast 静态扫描 scripts/people_merge.py
│  selfcheck       │ ──► 断言无网络模块 / 无进程派生 / 无动态代码执行
└──────────────────┘
```

### 子命令与中间契约说明

| 子命令 | 角色 | 输入 | 输出 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| `inspect` | 只读探测 | 多个源表格文件 | `profile.json` | 仅做格式嗅探、表头读取与样本抽样，不修改源文件，不执行合并 |
| `suggest-keys` | 键推荐 | `profile.json` / 源表数据 | `keys.json` | 对候选关联键进行打分并给出跨表重合度证据，辅助人工决策 |
| `merge` | 执行合并 | 源表 + `plan.json`（或 `--recipe`） | `汇总结果.xlsx` + `.report.json`（可选 `--save-recipe` 生成 `recipe.json`） | 按确认后的方案执行归一化、合并与输出；支持 `--backend auto/stdlib/openpyxl` |
| `selftest` | 端到端自测 | 内置测试用例 | 自测通过/失败状态 | 两阶段端到端闭环，覆盖纯 CSV 与跨格式混合合并 |
| `selfcheck` | 安全自审计 | 引擎源码 | AST 静态审计结果 | 离线验证引擎源码不存在外联、派生进程或动态代码执行 |

其中 `recipe.json` 用于固化经确认的合并方案（通过 `--save-recipe` 保存、`--recipe` 复用），便于 HR/行政在按月、按季度重复汇总同类报表时复用既定规则。

## 3. 格式嗅探与多源解析层

真实办公场景中，业务系统导出的文件常出现“扩展名与实际内容不符”（例如扩展名为 `.xls`，实际内容为 HTML 表格或文本文件）。因此引擎在读取阶段采用**内容嗅探优先，不单凭扩展名判断**的路由策略：

| 实际格式 | 解析机制 | 关键特性与边界 |
| :--- | :--- | :--- |
| `.xlsx` / `.xlsm` | `zipfile` + XML 解析（或 `openpyxl` 后端） | 仅读取工作表 XML 数据，**绝不执行 VBA 宏** |
| `.ods` | `zipfile` + `xml.etree`（ElementTree） | 纯标准库支持 OpenDocument 表格 |
| HTML 伪 `.xls` | `html.parser`（`HTMLParser`） | 解析首个 `<table>`，支持 `colspan` 跨列与 `<br>` 换行 |
| Excel 2003 XML（SpreadsheetML） | 统一安全 XML 解析 | 支持 `ss:Index` 跳列属性还原列位 |
| `.csv` / `.tsv` / `.txt` | `csv` + 编码/分隔符自动探测 | 自动识别 `utf-8-sig`、`utf-8`、`gb18030`、`gbk`、`big5` 编码与 `,`、`;`、`\t`、`|` 分隔符 |
| 旧版二进制 `.xls`（BIFF/OLE） | 可选依赖 `xlrd >= 2.0.1` | 未安装 `xlrd` 时直接拒收并提示用户另存为 `.xlsx` |
| PDF / 图片 / 扫描件 / 加密文件 | 显式拒收 | 超出结构化明文表格能力边界，拒绝静默降级 |

## 4. 关联键归一化与同义字段对齐

不同系统导出的人员表在格式习惯与列命名上存在差异。引擎在键推荐（`suggest-keys`）和合并（`merge`）阶段使用统一的归一化逻辑，同时**保留原始键值用于日志与未匹配追踪**。

```text
原始键值（如 "  ＥＭＰ-1001（曾用名） "）
   │
   ├─► 1. 去前后空格            ──► "ＥＭＰ-1001（曾用名）"
   ├─► 2. 全角转半角            ──► "EMP-1001(曾用名)"
   ├─► 3. 剔除括号内曾用名/别名  ──► "EMP-1001"
   └─► 4. 剥离工号跨系统前缀    ──► "1001"   （与另一表的 "1001" 命中同一键）
```

除键值归一化外，引擎还执行**同义列名归一**：
- 将语义相同但表述不同的列映射到同一逻辑字段（例如不同系统中的「手机」「联系电话」「联系方式」视为同一逻辑字段），用于在合并与冲突检测阶段进行跨表比对。
- 同义字段发生值不一致时，不会互相覆盖，而是保留各表原值并在状态列与日志中显式标出冲突字段。

## 5. 两个人工确认点的设计理由

本工具刻意**不做全自动静默合并**，而是在 `suggest-keys` 与 `merge` 之间设置两道确认关口：

### 确认点一：确认关联键（必须）
- **原因**：人员数据存在天然歧义。例如仅按「姓名」合并时，跨部门同名同姓员工会被错误拼接；不同系统的工号或缩写规则也可能存在局部碰撞。算法只能基于表头语义与值重合度给出证据（`keys.json`），最终由熟悉业务上下文的人员拍板确认关联键。
- **约束**：未经用户明确确认关联键，流程不进入 `merge`。

### 确认点二：确认未匹配记录处置策略（建议，一键确认）
- **原因**：不同汇总目的对“只在部分表中出现的人”处理诉求不同（例如核对漏打卡人员需单独拎出，制作在职总表则可能希望在主表标注或剔除）。
- **三种可选策略**：
  1. `separate_sheet`（**默认推荐**）：单独输出至 Sheet 3「未匹配记录」，保持主表干净且零数据丢失。
  2. `keep_marked`：保留在结果表中并打上状态标记。
  3. `drop`：直接剔除未匹配记录。

### 字段冲突处理原则：保留原值，绝不替用户选边
- 当同一关联键在多张源表的同一逻辑字段上存在不同取值时（例如招聘表与考勤表的手机号不一致），系统**不按时间或表顺序静默覆盖**，而是把各表原值以独立来源列完整保留，并在「数据状态」与「合并日志」中显式标记 `冲突：[字段名]`，把最终裁决权留给业务人员。

## 6. 双后端设计与一致性保障

针对 `.xlsx` 的读写，引擎内置双后端切换机制，由 `merge --backend <mode>` 控制：

```text
--backend 选路逻辑
   ├── auto（默认）──► 检测到已安装 openpyxl >= 3.1.0 ?
   │                      ├── 是 ──► 使用 openpyxl 后端（加速读写）
   │                      └── 否 ──► 自动回退 stdlib 后端（零依赖 ZIP+XML）
   ├── stdlib      ──► 强制使用标准库后端
   └── openpyxl    ──► 强制使用 openpyxl 后端
```

- **读取旧版 `.xls` 隔离**：二进制 `.xls` 仅在读取阶段通过可选依赖 `xlrd >= 2.0.1` 接入，写出产物始终统一为现代 `.xlsx` 格式。
- **双后端一致性校验**：`tests/test_backend_parity.py` 专门执行 `stdlib` 与 `openpyxl` 双后端的读写一致性断言，确保不论运行环境是否安装 `openpyxl`，输出的表格内容与业务语义保持一致；同时「合并日志」会记录本次实际使用的后端名称，保证可追溯性。

## 7. 输出契约

每次 `merge` 执行生成一份三 Sheet 的 Excel 文件（`汇总结果.xlsx`）与一份机器可读的伴随报告（`.report.json`）。

### 7.1 `汇总结果.xlsx` 三 Sheet 结构

#### Sheet 1：`汇总结果`
| 列位置 | 列名格式 | 内容说明 |
| :--- | :--- | :--- |
| 首列 | 归一化关联键 | 经过去空格、全半角转换、去括号别名与前缀剥离后的统一主键 |
| 中间列 | `原字段名（来源：文件名）` | 按来源表完整保留各表字段原值，避免静默覆盖与溯源丢失 |
| 末列 | `数据状态` | 标明该行匹配与一致性状态：<br>• `完整匹配`<br>• `部分缺失（缺：表A, 表B）`<br>• `冲突：[字段名]` |

#### Sheet 2：`合并日志`
作为审计底稿，记录本次合并的完整元数据与异常汇总：
- 基础元信息：执行时间、工具版本、实际使用的后端（`stdlib` / `openpyxl`）
- 输入与策略：文件统计、关联策略、整体匹配率
- 数据质量异常：表内重复键统计、空键统计、字段冲突清单
- 合规说明：免责声明

#### Sheet 3：`未匹配记录`
默认策略（`separate_sheet`）下承接未能完成跨表关联的记录，辅助人工核查拼写误差或离职/新增差异：
- `来源文件`
- `原始键值`
- `归一化键值`
- `最相近候选`（基于相似度提示可能对应的目标键）
- `数据行详情`

### 7.2 `.report.json` 伴随报告
- 以结构化 JSON 输出本次合并的统计指标与字段冲突明细，便于上游 Skill 代理读取并向用户汇报摘要，或供下游脚本进行二次检查与归档。

## 8. 安全架构与运行边界

由于人事表包含高度敏感的个人信息，且来源文件可能出自不可信的外部导出系统，架构在多个层级内置了防线：

### 8.1 运行时安全防线
1. **数据不出本机**：纯本地内存处理，不发起任何网络请求，不调用外部 API 或云端模型。
2. **统一 XML 安全入口 `_safe_xml`**：所有涉及 XML 的格式（`.xlsx` / `.xlsm` / `.ods` / SpreadsheetML）统一经过 `_safe_xml` 解析；一旦检测到 `<!DOCTYPE` 或 `<!ENTITY` 声明立即拒绝，阻断实体膨胀攻击（Billion Laughs）与外部 DTD 引用（XXE）。
3. **防资源耗尽上限**：
   - 单个 XML 成员解压上限：**64MB**（防 ZIP 炸弹）。
   - 重复列展开上限：**64**（防稀疏表格恶意重复声明撑爆内存）。
4. **宏安全**：解析 `.xlsm` 时仅读取工作表 XML 节点，绝不执行 VBA 宏。

### 8.2 静态代码自审计（`selfcheck`）
`scripts/people_merge.py selfcheck` 调用标准库 `ast` 解析引擎自身源码，静态断言源码中**不存在**：
- 网络模块导入或调用：`urllib`、`requests`、`socket`、`http`
- 系统命令/子进程派生：`os.system`、`subprocess`
- 动态代码执行：`eval`、`exec`

### 8.3 明确的适用边界与限制
- **规模上限**：单文件 **200MB**、单表 **20 万行**。
- **表头前提**：不支持多级合并单元格表头，输入前需整理为单行表头。
- **格式边界**：不支持 PDF、图片、扫描件及加密受保护文件。
- **定位边界**：定位为面向办公人员的本地汇总助手，不做直接写入数据库的严格 ETL 管道。

## 9. 后续扩展点

基于现有分阶段架构与契约边界，后续演进可在不破坏零依赖核心的前提下沿以下接缝扩展：

1. **输入格式适配器扩展**：解析层已通过内容嗅探与统一行结构解耦，新增格式只需增加嗅探特征与只读解析函数，并补齐 `tests/test_people_merge.py` 回归用例。
2. **归一化与同义词规则可配置化**：当前归一化规则（前缀剥离、括号别名剔除、同义列名映射）内置于引擎；后续可通过 `plan.json` / `recipe.json` 暴露组织自定义前缀表与同义词典，适配更多垂直系统命名习惯。
3. **表头预处理辅助**：针对当前不支持多级表头的限制，可在 `inspect` 阶段增加多级表头检测告警或可选的只读表头展平预览，降低人工整理成本。
4. **下游自动化衔接**：借助已有的 `.report.json` 结构化输出与 `--recipe` 复现机制，可低成本对接周期性报表校验脚本或上游 Skill 编排流程，而无需改动核心合并引擎。
