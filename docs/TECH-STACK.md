# 技术选型说明（TECH-STACK）

本文档记录「多表人员信息汇总助手」（`people-info-merge`，v1.0.0，2026-09-27 发布）的核心技术选型、决策依据、备选评估与架构取舍。项目面向 HR、行政与项目助理等非研发岗位，核心目标是在受限办公环境中实现安全、零门槛、可审计的多源人员表合并。

---

## 选型总览

| 选型维度 | 当前选型 | 主要备选方案 | 核心取舍 |
| :--- | :--- | :--- | :--- |
| 语言与运行时 | Python 3.9+ | Node.js、Go、Rust、VBA/Excel 宏 | 以主流系统预装/易部署与文本处理生态优先，放弃编译型语言的极致吞吐 |
| 核心依赖策略 | 零第三方依赖（纯 Python 标准库） | Pandas + NumPy、Polars | 牺牲 DataFrame 高级语法糖，换取极小体积、免编译与受限终端开箱即用 |
| 可选依赖 | `openpyxl >= 3.1.0`（MIT）、`xlrd >= 2.0.1`（BSD），均非必需 | 强制绑定第三方 Excel 库、全量自研 BIFF 二进制解析器 | 保持默认零依赖，同时为大表读写提速与旧版 `.xls` 提供渐进式增强 |
| 解析技术 | 内容嗅探 + 标准库流式/DOM 轻量解析（ZIP/XML/HTML/CSV） | 仅按扩展名路由、调用 LibreOffice/Excel COM 转换 | 规避跨平台外部二进制依赖与宏执行风险，放弃对加密文件与非表格格式的支持 |
| 测试栈 | 标准库 `unittest`（24 项回归断言）+ 内置 `selftest` | `pytest`、`tox`、外部 CI 专属测试框架 | 放弃第三方测试插件生态，确保目标环境零安装即可就地跑通全量验证 |

| 许可证 | MIT 许可证 | Apache-2.0、GPL-3.0 | 选择最宽松的商用与二次开发条款，与可选依赖（MIT / BSD）完全兼容 |

## 1. 语言与运行时

### 选择是什么
Python 3.9 及以上版本。

### 为什么这样选
- **标准库能力完整**：Python 标准库自带压缩（`zipfile`）、XML/HTML 解析（`xml.etree`、`html.parser`）、CSV 处理（`csv`）、Unicode 规范化（`unicodedata`）、模糊匹配（`difflib`）、命令行解析（`argparse`）与抽象语法树分析（`ast`），足以独立支撑完整引擎。
- **脚本级可读性与可审计性**：核心引擎为单文件纯源码（`scripts/people_merge.py`，约 1549 行），企业安全团队可直接审阅源码，并通过 `ast` 执行本地静态自检。
- **面向 Skill 生态友好**：无需针对 Windows、macOS、Linux 分别交叉编译发布多套二进制产物。

### 备选方案是什么
- **Go / Rust**：编译为单二进制文件，运行速度更快、无运行时依赖。
- **Node.js / TypeScript**：前端与自动化生态活跃，JSON 处理自然。
- **Excel VBA / Power Query**：贴近办公用户日常界面。

### 取舍在哪里
放弃了编译型语言在超大规模数据上的底层吞吐优势，换取源码透明可审计、跨平台零编译分发，以及对 Skill 规范和标准库生态的天然契合。对于 20 万行以内的办公表格场景，Python 3.9+ 原生数据结构已具备秒级完成能力。

---

## 2. 零依赖策略

### 选择是什么
核心引擎默认**零第三方依赖**，仅依赖 Python 标准库：`argparse`、`csv`、`json`、`re`、`difflib`、`unicodedata`、`zipfile`、`xml.etree`、`html.parser`、`unittest`、`datetime`（以及用于静态安全审计的 `ast`）。

### 为什么这样选
- **受限办公环境现实约束**：HR、行政、项目助理使用的企业办公电脑普遍存在无管理员权限、无法访问外网 PyPI、禁止安装第三方包等限制；零依赖保证只要具备 Python 3.9+ 即可直接运行。
- **避免重型依赖的体积与编译负担**：Pandas 含 C 扩展体积通常超过 100MB，且在不同系统架构与 Python 版本下容易触发编译环境或二进制 wheel 兼容问题。
- **性能足以覆盖目标规模**：办公人员表通常在 20 万行以内，使用 Python 原生字典、列表与集合完成索引、归一化与连接可在秒级内结束。

### 备选方案是什么
- **Pandas / Polars**：提供现成的 `read_excel`、`read_csv`、`merge` 等高阶 API，代码量更少。

### 取舍在哪里
团队承担了自行编写多格式表格解析、编码探测、关联键匹配与 XLSX 读写逻辑的维护成本，换来了近乎零部署门槛、可控的包体体积（远小于 10MB 上限）以及彻底消除第三方传递依赖带来的供应链风险。

---

## 3. 可选依赖

### 选择是什么
通过 `scripts/requirements.txt` 声明两个**均非必需**的可选依赖：
- `openpyxl >= 3.1.0`（MIT 许可）：用于 `.xlsx` 读写加速。
- `xlrd >= 2.0.1`（BSD 许可）：仅用于读取旧版二进制 `.xls`（BIFF/OLE）文件。

### 为什么这样选
- **性能与兼容性渐进增强**：在允许安装依赖的环境中，装上 `openpyxl` 可提升较大 `.xlsx` 文件的读写效率；遇到老旧 HR/考勤系统导出的二进制 `.xls` 时，装上 `xlrd` 即可直接读取。
- **安全优雅降级**：未安装 `openpyxl` 时，引擎自动回退至标准库后端，功能契约保持一致；未安装 `xlrd` 时，明确提示用户先在办公软件中另存为 `.xlsx`，而非抛出晦涩报错或静默失败。

### 备选方案是什么
- **将 `openpyxl` / `xlrd` 设为强依赖**：简化后端分支代码，但直接破坏受限环境的开箱即用能力。
- **自研 BIFF/OLE 二进制 `.xls` 解析器**：代码复杂度极高、历史边缘格式众多，投入产出比低。

### 取舍在哪里
引入了 `stdlib` 与 `openpyxl` 双后端并存的维护成本（需通过一致性测试持续校验输出对齐）；但换取了“零依赖保底 + 有依赖提速/补齐旧格式”的平衡体验。

## 4. 解析技术

### 选择是什么
采用**内容嗅探（不轻信文件扩展名）+ 分格式轻量解析**的技术路线：
- `.xlsx` / `.xlsm`：`zipfile` + XML 解析（仅读取表格数据，绝不执行 VBA 宏）。
- `.ods`：`zipfile` + `xml.etree`（ElementTree）。
- HTML 伪 `.xls`：`html.parser`（`HTMLParser`）解析首个 `<table>`，支持 `colspan` 与 `<br>` 换行。
- Excel 2003 XML（SpreadsheetML）：XML 解析，支持 `ss:Index` 跳列属性。
- `.csv` / `.tsv` / `.txt`：自动识别 `utf-8-sig`、`utf-8`、`gb18030`、`gbk`、`big5` 编码，以及 `,`、`;`、`\t`、`|` 分隔符。
- 旧版二进制 `.xls`（BIFF/OLE）：委托可选依赖 `xlrd`，未安装时提示另存为 `.xlsx`。

### 为什么这样选
- **贴合国内企业系统导出实况**：大量老旧 OA、考勤机、招聘后台导出的 `.xls` 文件实质上是 HTML 表格、SpreadsheetML 或 GBK 编码的文本文件；仅看后缀名会直接解析失败。
- **无外部进程依赖**：不依赖本机是否安装 Microsoft Excel、WPS 或 LibreOffice。

### 备选方案是什么
- **调用 LibreOffice Headless / Excel COM 接口统一转码**：格式兼容性广，但依赖重型外部软件、跨平台表现不一且存在进程安全风险。
- **引入通用文档抽取库（支持 PDF/OCR）**：扩大输入范围，但会引入庞大依赖且识别准确率不可控，违背人事数据高确定性要求。

### 取舍在哪里
明确放弃对 PDF、图片、扫描件、加密文件以及多级复杂表头的支持（要求先整理为单行表头），换取解析行为确定、零外部进程依赖、内存可控与跨平台一致。

## 5. 测试栈

### 选择是什么
- **回归测试框架**：Python 标准库 `unittest`，共包含 **24 项回归断言**：
  - `tests/test_people_merge.py`（23 项）：覆盖全格式解析、拒收场景与核心业务逻辑。
  - `tests/test_backend_parity.py`（1 项）：专门校验标准库后端与 `openpyxl` 后端的读写一致性。
- **内置端到端自测**：核心引擎自带 `selftest` 子命令，执行两阶段自测（阶段一：CSV 合并；阶段二：HTML 伪 `.xls` + `.ods` + `.tsv` 跨格式合并）。
- **测试数据**：`examples/sample_data/` 提供虚构脱敏样本（招聘、考勤、培训三表 CSV + 旧系统 HTML 伪 `.xls`）。

### 为什么这样选
- **与零依赖策略一脉相承**：`unittest` 随 Python 发行版自带，任何使用者或审计方无需 `pip install pytest` 即可直接运行回归套件。
- **运行时可自证**：`selftest` 将最小可验证闭环打包进主程序本身，方便在交付后的隔离环境中快速确认功能完好。

### 备选方案是什么
- **`pytest`**：断言语法更简洁、fixture 与参数化能力更强，但需要额外安装第三方包。

### 取舍在哪里
牺牲了 `pytest` 的简洁断言语法与丰富插件生态，换取测试环境零配置、离线可运行，以及“交付产物自带自检能力”的工程闭环。

## 6. 安全栈

### 选择是什么
围绕“本地数据处理 + 恶意文件防御 + 静态代码自证”三层设计，全部基于标准库实现：
- **纯本地内存处理**：不联网、不调用外部 API 或云端大模型，敏感人事信息不出本机。
- **统一 XML 安全入口 `_safe_xml`**：解析前遇到 `<!DOCTYPE` 或 `<!ENTITY` 直接拒绝，防御实体膨胀攻击（Billion Laughs）与外部 DTD 引用（XXE）。
- **资源边界限制**：单个 XML 解压上限 64MB，重复列展开上限 64；业务层面限制单文件 200MB、单表 20 万行。
- **内置静态安全审计（`selfcheck`）**：使用标准库 `ast` 遍历源码语法树，断言无网络模块（`urllib`/`requests`/`socket`/`http`）、无系统进程派生（`os.system`/`subprocess`）、无动态代码执行（`eval`/`exec`）。
- **宏隔离**：读取 `.xlsm` 时仅解析 XML 数据节点，绝不执行 VBA 宏。

### 为什么这样选
- 人事汇总表通常包含姓名、工号、联系方式等敏感个人信息，企业合规对“无外联、无隐藏命令执行、抗畸形文件”有硬性要求。
- 通过 `selfcheck` 将安全承诺转化为可重复执行的自动化断言，而非仅停留在文档声明。

### 备选方案是什么
- **引入 `defusedxml`**：成熟的 XML 安全解析库，但会破坏核心零依赖原则。
- **依赖外部 SAST 工具（如 Bandit、Semgrep）**：扫描规则更全面，但无法随工具交付给终端用户在本地一键复验。

### 取舍在哪里
手写 `_safe_xml` 与 `ast` 审计规则的覆盖面聚焦于本项目实际攻击面（XML 解析、外联、命令执行、动态执行），不如通用 SAST 平台全面；但实现了零额外依赖、随程序内建、随时可离线自证的安全闭环。

## 7. 打包方式

### 选择是什么
使用自研轻量脚本 `scripts/package_skill.py`（约 90 行）打包为 Skill 分发产物。打包过程自动校验 `SKILL.md` 位于根层级、排除缓存与临时产物，最终包体远小于 10MB 上限。

### 为什么这样选
- **契合 Skill 交付契约**：需要严格保证 `SKILL.md` 的根路径位置与目录整洁度，避免把 `__pycache__`、临时输出或测试残留打入发布包。
- **透明可控**：约 90 行纯标准库脚本即可完成校验与归档，无额外构建工具链依赖。

### 备选方案是什么
- **PyInstaller / Nuitka 打包为独立可执行文件**：免除用户安装 Python，但产物动辄数十 MB（超过 10MB 上限），且易触发企业终端杀毒软件误报，同时失去源码可审计性。
- **标准 Python Wheel / PyPI 发布**：适合研发通过 `pip` 安装，但不直接满足 Skill 目录契约，且对无外网办公机不友好。

### 取舍在哪里
要求运行环境已具备 Python 3.9+，换来了极小包体（远低于 10MB）、跨平台通用单一产物、源码透明可审计以及与 Skill 平台的无缝集成。

## 8. 许可证

### 选择是什么
项目采用 **MIT 许可证**（详见仓库根目录 `LICENSE`）。

### 为什么这样选
- **采用门槛最低**：允许企业内部使用、修改、集成与再分发，无需承担传染性开源义务，符合办公效率工具在组织内广泛落地的诉求。
- **依赖兼容性清晰**：可选依赖 `openpyxl` 采用 MIT 许可，`xlrd` 采用 BSD 许可，两者均为宽松许可证，与本项目 MIT 许可完全兼容，无合规冲突。

### 备选方案是什么
- **Apache-2.0**：增加明确的专利授权条款，但条款篇幅较长。
- **GPL-3.0**：强 Copyleft 约束，容易阻碍企业内部二次封装与集成。

### 取舍在哪里
MIT 许可证本身不包含显式专利授权与强 Copyleft 约束，但以极简清晰的法律文本最大化降低了个人与企业用户的法务评估成本。
